HILLBCS Chats • SSO Integration

Chat SSO Integrator Guide

Connect an upstream app such as Hiring Hall or Workspace to HILLBCS Chats using a provider-specific API key. The source system does not need to generate Chat JWTs directly.

No Chat-side signup Provider-scoped user isolation Server-to-server bootstrap

Overview

Chat exposes a provider-aware bootstrap endpoint. The source app calls the endpoint from its backend, receives a short-lived login URL, then redirects the browser into Chat.

Recommended identity model: use provider_user_id as the stable upstream identity and treat email as a profile field rather than the primary cross-system key.

Chat Configuration

Each upstream app needs its own provider block in hillbcs-chats. Every provider must have a dedicated API key and SSO secret.

Relevant Chat env vars

.env 
CHAT_SSO_WORKSPACE_SECRET=...
CHAT_SSO_WORKSPACE_API_KEY=...
HILLBCS_WORKSPACE_URL=https://workspace.hillbcs.com

CHAT_SSO_HIRE_SECRET=...
CHAT_SSO_HIRE_API_KEY=...
HILLBCS_HIRE_URL=https://hire.hillbcs.com
Do not reuse keys across providers. Workspace and Hiring Hall should keep separate API keys and separate SSO secrets to preserve isolation and safe rotation.

API Endpoint

POST /api/integrations/sso/login-url

Request headers

HTTP 
X-API-KEY: <provider-api-key>
Accept: application/json
Content-Type: application/json

Request body

JSON 
{
  "provider_user_id": "123",
  "email": "user@example.com",
  "name": "Jane Doe",
  "avatar": "https://hire.hillbcs.com/storage/avatars/jane.jpg",
  "role": "employee",
  "source_url": "https://hire.hillbcs.com/dashboard",
  "redirect_to": "/chat"
}

Request fields

Field Required Description
provider_user_id Yes Stable unique id from the source app.
email Yes User email from the source app.
name Yes User display name.
avatar No Avatar URL used to hydrate the Chat profile.
role No Source-system role value if needed for display or policy.
source_url No Return destination for “Back to App” inside Chat.
redirect_to No Desired in-Chat route after login, usually /chat.

Success response

JSON 
{
  "success": true,
  "provider": "hire",
  "expires_in": 60,
  "login_url": "https://chat.hillbcs.com/sso/login?token=...",
  "token": "..."
}

Integration Flow

  1. User is already authenticated inside the source app.
  2. Source backend calls Chat’s login-url endpoint.
  3. Chat validates the provider API key and mints a short-lived SSO token.
  4. Source app receives login_url.
  5. Source app redirects the browser into Chat.
  6. Chat logs the user in and restores the provider-scoped identity.
Important: call the bootstrap endpoint from the server. Never expose the provider API key in frontend JavaScript.

Laravel Example

This is the recommended pattern for apps such as hillbcs-hire.

Source app env

.env 
CHAT_BASE_URL=https://chat.hillbcs.com
CHAT_SSO_API_KEY=replace-with-hire-provider-api-key

Source app config

PHP Config 
'chat' => [
    'base_url' => env('CHAT_BASE_URL'),
    'api_key' => env('CHAT_SSO_API_KEY'),
],

Controller example

PHP 
<?php

namespace App\Http\Controllers;

use Illuminate\Http\RedirectResponse;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\Http;

class ChatSsoController extends Controller
{
    public function redirectToChat(Request $request): RedirectResponse
    {
        $user = $request->user();

        $response = Http::acceptJson()
            ->withHeaders([
                'X-API-KEY' => config('services.chat.api_key'),
            ])
            ->post(rtrim(config('services.chat.base_url'), '/').'/api/integrations/sso/login-url', [
                'provider_user_id' => (string) $user->id,
                'email' => (string) $user->email,
                'name' => (string) $user->name,
                'avatar' => $user->avatar_url,
                'role' => $user->role ?? 'user',
                'source_url' => url('/dashboard'),
                'redirect_to' => '/chat',
            ]);

        abort_unless($response->successful(), 502, 'Chat SSO bootstrap failed.');

        $loginUrl = (string) data_get($response->json(), 'login_url', '');
        abort_if($loginUrl === '', 502, 'Chat login URL missing.');

        return redirect()->away($loginUrl);
    }
}

Route example

Routes 
Route::middleware('auth')
    ->get('/sso/chat', [ChatSsoController::class, 'redirectToChat'])
    ->name('sso.chat');

Integrator Notes

  • Call the endpoint from the server, not frontend JavaScript.
  • Treat the provider API key as a secret.
  • Each provider must have its own API key.
  • The returned login_url is short-lived and currently expires in 60 seconds.
  • provider_user_id must stay stable for the lifetime of the upstream user.

Maintainer Notes

  • Run provider-identity migrations before onboarding another app.
  • Keep provider API keys and SSO secrets separate.
  • If the same email exists in multiple providers, preserve provider isolation and use explicit linking where needed.
  • Any email-only admin or API surface must become provider-aware once duplicate emails exist.

Quickstart

  1. Configure provider env vars in Chat.
  2. Give the integrator a provider API key.
  3. Call /api/integrations/sso/login-url from the source backend.
  4. Redirect the browser to login_url.

Provider Isolation

Workspace users only see Workspace users. Hiring Hall users only see Hiring Hall users.

  • Search is provider-scoped
  • DM creation is provider-scoped
  • Group membership is provider-scoped
